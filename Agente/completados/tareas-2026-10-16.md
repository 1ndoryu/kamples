## 16A-4 — Protección de datos: verificar antes de volcar y antes de restaurar

- **Qué se hizo:** la viñeta 150 del roadmap («un error pasado hizo que se borrara
  la base de datos») se llevó a código. Dos defectos reales con la firma del
  incidente: `backup-postgres.sh` dejaba un `.dump` de 0 bytes con nombre
  plausible cuando el `exec` fallaba (el redirect ya había creado el archivo), y
  el runbook de deploy restauraba con `pg_restore --clean --if-exists` sin
  verificar el dump. Ahora el criterio de aceptación vive en un solo sitio
  (`scripts/lib/dump-postgres.sh`) y lo comparten el camino manual y el sidecar.
- **Archivos:** `scripts/lib/dump-postgres.sh` (nuevo), `scripts/restore-postgres.sh`
  (nuevo), `scripts/backup-uploads.sh` (nuevo), `scripts/migrar.sh` (nuevo),
  `scripts/guardia-migraciones.sh` (nuevo), `scripts/lib/migraciones.sh` (nuevo),
  `migrations/.destructivas-permitidas` (nuevo), `scripts/backup-postgres.sh`,
  `scripts/backup-postgres-loop.sh`, `docker-compose.yml`, `package.json`,
  `.gitignore`, `Agente/documentacion/deploy/proteccion-datos-2026-10-16.md`,
  `Agente/planes/plan-deploy-coolify-2026-06-30.md`.
- **Evidencia:** `npm run bd:test` → 25/25; contra `pg_dump`/`pg_restore` reales en
  la 89 → 5/5 (la base vacía de 913 B se rechaza, la de 3416 B con datos se acepta,
  el mismo dump truncado a 100 B se rechaza, con la cabecera pisada se rechaza, y
  esquema sin filas se acepta); `npm run bd:guardia` sobre las 24 migraciones
  reales → 1 destructiva declarada, 0 falsos positivos.
- **Decisiones:** el umbral de bytes no es el criterio (el de 4096 rechazaba bases
  legítimas pequeñas: la firma de una base vacía es no tener ninguna entrada
  `TABLE DATA`); `PG_EXEC` es la única pieza que cambia entre entornos, y en
  producción es obligatorio el de coolify-manager-rs (AGENTS §10).
- **Pendiente y reservado a la usuaria:** copia off-site y ensayo de restauración
  real contra el stack de producción.

## 16A-4 — admin/panel: la tab abierta sobrevive a la recarga (viñeta 108)

- **Qué se hizo:** el panel de admin volvía siempre a `usuarios` al recargar. La
  causa no era el orden de restauración —`setTabs` ya prioriza `?tab=` > memoria
  > tab inicial— sino que `tabsPorIsla`, la memoria keep-alive, vivía solo en
  memoria y el panel de admin **nunca escribe `?tab=`** en la URL: solo lo hacen
  las islas que usan `useUrlFiltros`. Ahora esa memoria se persiste en
  `sessionStorage`.
- **Archivos:** `frontend/src/legacy/stores/varios-4/tabsTopBarStore.ts`.
- **Evidencia:** `npm --prefix frontend run type-check` en la 89 → 0 errores.
  Prueba contra el store **real** (empaquetado con esbuild desde
  `frontend/node_modules`, no una copia) en `/var/tmp/prueba-108/prueba.mjs`:
  **8/8**, con el «recargar» simulado por una importación nueva del módulo. Cubre
  primera visita, cambio de tab + recarga, `?tab=` ganando sobre la memoria, una
  tab guardada que ya no existe y dos islas conservando la suya por separado.
  `Arranque gate "KAMPLES" --cierre` → 0 nuevos, 0 resueltos.
- **Decisiones:** `sessionStorage` y no `localStorage`, porque la tab abierta es
  estado de la pestaña: con `localStorage` dos pestañas en islas distintas se
  pisarían la memoria. `partialize` deja fuera `tabs`, `activa` e
  `islaTabsActual`: describen lo que hay pintado y se recalculan al montar.
- **Pendiente (deuda de herramienta, no de KAMPLES):** `frontend` no tiene runner
  de tests, así que esta prueba no queda como regresión versionada; el arnés vive
  en `/var/tmp`.
